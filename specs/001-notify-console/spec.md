# Feature Specification: 托盘通知控制台

**Feature Branch**: `001-notify-console`

**Created**: 2026-11-06

**Status**: Draft

**Input**: 用户描述——「在本托盘插件内集成 DSH 通知能力，并把托盘脚本拓展为多平台版本」；
经头脑风暴收敛为：托盘成为唯一投递点，DSH 侧只做事件采集；面板同时承担状态、操作与通知回查。

## 范围边界

本规格只覆盖**通知能力与托盘面板**（下表 S1+S2）。多平台底座（S3）是独立规格，
本规格只规定它必须满足的接口要求，不规定它怎么实现。

| | 内容 | 是否本规格 |
|---|---|---|
| S1 | 事件采集 → 通知投递 → 点击回会话 | ✅ |
| S2 | 托盘面板：控制区 + 未查看 / 已查看 / 工作中 / 概览 | ✅ |
| S3 | 平台抽象层与 Windows 支持 | ❌ 另立规格 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 离开电脑后知道「跑完了」或「需要我」 (Priority: P1)

用户在 DSH 里派了一个长任务，切到浏览器或终端做别的事。任务结束时，桌面上出现一条
系统通知；如果任务中途停下来等审批或等你回答问题，出现的通知优先级更高、不会被忽略。

**Why this priority**: 这是整个功能的唯一目的——不看屏幕也能知道该回来了。
没有它，其余功能都只是锦上添花。

**Independent Test**: 在一个会话里发起一个需要审批的工具调用，然后切走窗口；
应收到「需要你审批」通知。再让一个会话正常跑完，应收到「已完成」通知。

**Acceptance Scenarios**:

1. **Given** DSH 在运行且托盘在线，**When** 某会话的轮次以「完成」结束，
   **Then** 出现一条完成通知，标题含会话名，正文含该轮的工具调用次数与耗时。
2. **Given** 同上，**When** 某会话停下来请求工具审批，**Then** 立即出现一条「需要你审批」
   通知，正文含工具名与关键参数摘要。
3. **Given** 同上，**When** 某会话调用提问工具等待回答，**Then** 立即出现「等待你回答」通知。
4. **Given** 某轮以错误、阻塞或超出输出上限结束，**When** 该事件发生，**Then** 通知归入
   「出错」类别而非「完成」，并带上可据以判断的错误摘要。
5. **Given** 用户在设置里关闭了「完成」类通知，**When** 轮次完成，**Then** 不出现完成通知，
   但「需要你」类通知照常出现。

---

### User Story 2 - 点通知直接回到那个会话 (Priority: P1)

用户看到通知，点一下，浏览器打开 DSH 并**直接定位到产生这条通知的那个会话**，
而不是首页让用户自己找。

**Why this priority**: 多会话并行时，「打开 UI 再找会话」是通知价值的一半；
不能跳转的通知会退化成骚扰。

**Independent Test**: 同时开三个会话，让其中一个结束；点该通知，
应落在那个会话的对话视图，而不是别的会话或首页。

**Acceptance Scenarios**:

1. **Given** 一条针对会话 A 的通知，**When** 用户点击它，**Then** 打开的页面停在会话 A。
2. **Given** 会话 A 已被删除，**When** 用户点击它的通知，**Then** 打开 DSH 首页并提示该会话已不存在，
   不出现白屏或错误弹窗。
3. **Given** 用户重复点击同一条通知，**When** 第二次点击，**Then** 复用已打开的页面而不是再开一个标签。
4. **Given** 页面被刷新，**When** 刷新完成，**Then** 不会因为地址栏里残留的定位参数再次跳转。

---

### User Story 3 - 面板里看「谁在跑、跑了多久」 (Priority: P2)

用户左键点托盘图标打开面板，切到「工作中」，一眼看到当前哪些会话在跑、各跑了多久、
正在执行什么；停下来等你回答的会话被标出来。

**Why this priority**: 并行多个会话时，用户需要判断「该等还是该催」；
但它是辅助判断，不承担「叫你回来」的核心职责。

**Independent Test**: 启动两个会话，一个正常跑、一个卡在提问；打开面板「工作中」，
应看到两行，第二行带「等你回答」标记，时长每秒递增。

**Acceptance Scenarios**:

1. **Given** 有两个会话在运行，**When** 打开「工作中」，**Then** 两行分别显示会话名、轮次序号、已运行时长、当前工具。
2. **Given** 「工作中」页处于打开状态，**When** 时间流逝，**Then** 时长每秒递增，且不因数据刷新而跳变或回退。
3. **Given** 某会话在等待审批或回答，**When** 出现在该页，**Then** 以区别于普通运行的标记呈现。
4. **Given** 所有会话都空闲，**When** 打开该页，**Then** 显示空状态而不是过期条目。

---

### User Story 4 - 概览里看 DSH 的子进程开销 (Priority: P2)

面板「概览」列出 DSH 拉起的子进程（主进程、MCP 服务器、工具子进程），
显示各自的 CPU 与内存占用，以及合计。

**Why this priority**: 排查「DSH 为什么卡」时最直接的证据；但它只在用户主动查看时有用。

**Independent Test**: 启动一个长跑工具，打开「概览」，应看到该工具进程出现在列表中且 CPU 明显高于空闲进程。

**Acceptance Scenarios**:

1. **Given** DSH 在运行且面板打开，**When** 切到「概览」，**Then** 列出子进程，含角色标签、标识、CPU 百分比、内存占用。
2. **Given** 面板首次打开，**When** 第一次采样完成，**Then** CPU 列显示为「待采样」而不是 0%，避免误报空闲。
3. **Given** 面板关闭，**When** 用户不再查看，**Then** 停止采样，不产生持续开销。
4. **Given** DSH 已停止或卡死，**When** 打开「概览」，**Then** 仍能展示可获取的信息并明确说明当前状态。

---

### User Story 5 - 在设置页决定提醒哪些事 (Priority: P2)

用户在 DSH 的设置页找到「通知」分区，选一个预设（安静 / 标准 / 详细），
再按需打开或关闭具体事件类型；改动立即生效，不需要重启。

**Why this priority**: 噪音是通知功能最常见的失败原因；没有开关，用户会直接关掉整个功能。

**Independent Test**: 把预设切到「安静」，触发一次轮次完成，不应有通知；切回「标准」，再触发，应有通知。

**Acceptance Scenarios**:

1. **Given** 用户从未改过设置，**When** 首次使用，**Then** 处于「标准」预设。
2. **Given** 用户选择「安静」「标准」或「详细」，**When** 选择生效，**Then** 各类事件的开关注入该预设的默认值。
3. **Given** 用户单独改动某一类开关，**When** 改动保存，**Then** 界面标明当前已偏离预设（显示为「自定义」）。
4. **Given** 用户点「发送测试通知」，**When** 点击，**Then** 立即出现一条测试通知，用于确认链路通畅。
5. **Given** 两个窗口同时打开设置页，**When** 一方保存，**Then** 另一方保存时被拒绝并提示重新加载，而不是静默覆盖。

---

### User Story 6 - 事后回查「之前那条通知」 (Priority: P3)

用户关掉了通知，或当时没空处理。事后打开面板「已查看」，按日期分组找到那条记录，
点进去回到对应会话。

**Why this priority**: 提升长期可用性，但不是首次使用的必需路径。

**Independent Test**: 点击一条未查看通知使其转为已查看，关闭面板再打开，该条目仍在「已查看」里且可点击跳转。

**Acceptance Scenarios**:

1. **Given** 一条未查看通知，**When** 用户点击它，**Then** 它移入「已查看」且未被删除。
2. **Given** 「已查看」中有跨多天的条目，**When** 打开该页，**Then** 按日期分组显示（今天 / 昨天 / 更早）。
3. **Given** 历史条目数量达到上限，**When** 新增条目，**Then** 最旧的条目被淘汰，且不出现文件无限增长。
4. **Given** 托盘重启，**When** 重新打开面板，**Then** 已查看历史完整保留。

---

### User Story 7 - 托盘不在时也不丢事件 (Priority: P3)

用户从终端直接启动 DSH，没有开托盘。事后启动托盘时，应看到这段时间内错过的通知摘要，
而不是一片空白。

**Why this priority**: 防止「以为会提醒却什么都没发生」的失望；属于健壮性补强。

**Independent Test**: 关闭托盘，触发两条通知，再启动托盘；应看到「错过 N 条」的提示，并能查看它们。

**Acceptance Scenarios**:

1. **Given** 托盘未运行，**When** DSH 产生通知事件，**Then** 事件被保留而非丢弃。
2. **Given** 托盘启动时存在未消费的保留事件，**When** 托盘就绪，**Then** 这些事件进入未查看列表并给出汇总提示。
3. **Given** 保留的事件过旧（超过保留期限），**When** 托盘启动，**Then** 不投递这些陈旧通知，只清理掉。

---

### User Story 8 - 与既有的「可能卡住」提示兼容 (Priority: P3)

另一个 DSH 插件（负责在模型反复不声明完成时提醒用户）会在会话里插入提示消息。
这些提示目前只有打开会话才看得到；本功能应把它们也抬成通知，但不需要那个插件做任何改动。

**Why this priority**: 它让既有能力立刻变得可感知，是低成本高回报；但它依赖别人的数据形状，
不适合作为核心路径。

**Independent Test**: 让一个会话触发该插件的提醒，应收到一条「提示」类通知，且会话内仍保留原提示。

**Acceptance Scenarios**:

1. **Given** 会话中插入了一条带「提示」来源的消息，**When** 该消息写入会话，**Then** 出现一条通知，标题标明来源、正文为该提示的一行摘要。
2. **Given** 用户关闭了该类通知，**When** 提示再次出现，**Then** 不弹通知，会话内提示不受影响。
3. **Given** 该插件升级并更改了文案，**When** 提示再次出现，**Then** 本功能仍能识别并投递（不依赖其文案内容）。

---

### Edge Cases

- **通知服务不支持操作按钮**：某些桌面环境的通知服务不接受「点击动作」。
  此时通知仍要出现，点击退化为打开面板；不得因为无法附加动作而整条通知失败。
- **免打扰 / 通知被系统屏蔽**：系统不弹窗时，面板里的未查看计数仍然准确，不得因此丢条目。
- **同一事件重复到达**：同一会话同一轮次的同一事件被投递两次时，只出现一条通知。
- **父会话结束时子会话仍在跑**：完成通知应等子会话结束后再发；等待超时则丢弃而不是误报完成。
- **会话被删除后再收到其事件**：忽略，不产生指向不存在会话的通知。
- **系统时钟回拨**：已查看历史的日期分组不得因此错乱；相对时间显示为「刚刚」而不是负数。
- **通知正文过长**：截断并保留可读的结尾，不得整段回显命令或路径。
- **托盘在 DSH 之前启动**：DSH 起来后自动接上，不需要用户重启托盘。
- **DSH 异常退出**：「工作中」页不得继续显示已死的会话；状态转为未知并提示。
- **两个托盘实例**：第二个直接退出（既有行为），通知不被两边同时投递。
- **无可用系统托盘宿主**：托盘按既有行为退出并说明原因；此时通知能力不可用，不得静默常驻。

## Requirements *(mandatory)*

### Functional Requirements

**事件采集与筛选**

- **FR-001**: 系统 MUST 从 DSH 采集以下事件：轮次开始与结束、审批请求、提问请求、
  后台任务结算、目标状态变化、工具执行结果、上下文压缩、会话内提示消息。
- **FR-002**: 系统 MUST 把事件归入四组——「需要你」（审批、提问）、「完成与出错」、
  「提示」（会话内插入的来源归属提示）、「其它信息性」（后台任务、目标、工具失败、压缩），
  并允许逐组开关。
- **FR-003**: 系统 MUST 把轮次结束按原因分为完成、出错、阻塞、超限、取消、中断六类，
  其中取消与中断默认不通知。
- **FR-004**: 系统 MUST 忽略子会话的轮次结束，除非用户显式开启「子任务」通知。
- **FR-005**: 系统 MUST 在父会话结束而仍有子会话运行时挂起完成通知，
  待最后一个子会话结束后再判定；挂起超过上限（15 分钟）则丢弃，不得误报完成。
- **FR-006**: 系统 MUST 对同一会话同一轮次的同一事件去重。

**预设与设置**

- **FR-007**: 系统 MUST 提供三个预设——安静（「需要你」+「提示」）、
  标准（另含完成与出错）、详细（全量），并记住用户选择。
  安静预设保留「提示」，因为它承载的是「你可能卡住了」这类必须告知的信息，
  与「只提醒必须由人介入的事」并不冲突。
- **FR-008**: 系统 MUST 允许逐**组**覆盖预设默认值（「需要你」组内再拆审批 / 提问两个子项）；
  一旦覆盖，界面 MUST 标明当前为「自定义」。
- **FR-009**: 设置变更 MUST 立即生效，不需要重启 DSH 或托盘。
- **FR-010**: 设置 MUST 在并发修改时检测冲突并拒绝过期写入，而不是静默覆盖。

**投递**

- **FR-011**: 系统 MUST 只由一个进程投递系统通知，避免同一事件出现两条通知。
- **FR-012**: 系统 MUST 在投递失败时保留该条目于面板列表，不得因投递失败丢失记录。
- **FR-013**: 「需要你」类通知 MUST NOT 自动消失（或使用系统允许的最长驻留时长）；
  信息性通知 MUST 按系统默认时长自动消失，不长期占据通知区。
- **FR-014**: 系统 MUST 在通知正文中避免出现访问令牌等敏感信息。

**点击与定位**

- **FR-015**: 通知 MUST 携带足以定位到具体会话的信息。
- **FR-016**: 点击通知 MUST 打开 DSH 并定位到该会话；会话已不存在时 MUST 落到首页并说明。
- **FR-017**: 定位参数 MUST 在使用后被移除，刷新页面不得重复跳转。
- **FR-018**: 点击 MUST 复用已打开的页面，而不是每次新开标签。

**面板**

- **FR-019**: 左键点击托盘图标 MUST 打开面板；右键 MUST 提供快捷菜单（既有菜单项保留）。
- **FR-020**: 面板顶部 MUST 常驻显示当前状态（未运行 / 启动中 / 运行中·自有 / 运行中·接管 / 停止中 / 失败）
  与元信息（进程标识、端口、启动来源、是否持有令牌）。
- **FR-021**: 面板 MUST 提供启动、停止、重启、打开 Web UI 四个操作，并按状态启用或禁用。
- **FR-022**: 停止与重启 MUST 保留确认对话框，且默认按钮为「取消」。
- **FR-023**: 接管实例（无令牌）时，面板 MUST 说明未授权成因与一键修复路径。
- **FR-024**: 面板 MUST 有四个标签页：未查看、已查看、工作中、概览；标签等宽且文字居中，计数标记不影响文字位置。
- **FR-025**: 未查看 MUST 显示未读计数，并在托盘图标上以徽标反映同一数字。
- **FR-026**: 点击未查看条目 MUST 将其移入已查看，且不删除。
- **FR-027**: 已查看 MUST 按日期分组并长期保留，保留上限为 500 条 / 30 天。
- **FR-028**: 工作中 MUST 显示每个活动会话的会话名、轮次序号、已运行时长、当前工具，
  并对等待用户输入的会话加以区分。
- **FR-029**: 工作中的时长 MUST 由本地累加，每秒更新，且不因数据刷新而跳变或回退。
- **FR-030**: 概览 MUST 列出 DSH 子进程的角色、标识、CPU 百分比、内存占用与合计。
- **FR-031**: 概览的 CPU 首次采样 MUST 显示为待采样状态，而不是 0%。
- **FR-032**: 概览采样 MUST 只在面板可见时进行，面板关闭即停止。
- **FR-033**: 概览 MUST 说明其 CPU 与内存口径（单核百分比、RSS 求和含共享页重复计算）。

**降级与持久化**

- **FR-034**: 托盘未运行时产生的事件 MUST 被保留，并在托盘下次启动时进入未查看列表。
- **FR-035**: 保留事件超过保留期限 MUST 被清理而不投递。
- **FR-036**: 托盘 MUST 在 DSH 启动或重启后自动接上，不需要用户手动重连。
- **FR-037**: 面板状态与历史 MUST 跨托盘重启保留。

**兼容**

- **FR-038**: 系统 MUST 把带「提示」来源标记的会话内消息抬成通知，且不要求该来源做任何改动。
- **FR-039**: 该识别 MUST 基于来源标识与消息形态，而非具体文案内容。
- **FR-040**: 系统 MUST NOT 把通知写回会话内容，不得影响模型上下文。

**平台**

- **FR-041**: 通知投递、点击定位与面板能力 MUST NOT 依赖 Linux 专有机制而无法在其他平台实现；
  平台差异 MUST 收敛在单一层内，其余逻辑不出现平台分支。
  各平台的**等效实现**由多平台底座规格交付，本规格只约束接口形态。

### Key Entities

- **通知条目**：一条可被感知的事件记录。属性含类别、会话标识、会话标题、标题文案、正文、
  发生时刻、已查看状态、定位信息、去重标识。生命周期为「未查看 → 已查看 → 淘汰」。
- **会话状态条目**：一个会话当前的运行态。属性含会话标识、标题、状态（运行 / 等待用户 / 空闲）、
  轮次序号、轮次开始时刻、当前工具。存在期为会话处于活动状态期间。
- **进程采样条目**：一次采样中某个子进程的开销。属性含标识、角色、CPU 百分比、内存占用。
  仅存在于面板打开期间。
- **预设**：一组事件开关的默认值集合，分安静 / 标准 / 详细三档，可被逐项覆盖形成「自定义」。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 从事件发生到通知可见，90% 的情况在 2 秒内完成。
- **SC-002**: 从点击通知到目标会话可交互，90% 的情况在 3 秒内完成（含浏览器聚焦）。
- **SC-003**: 在「标准」预设下连续使用 8 小时，通知条数不超过实际轮次数的 1.1 倍
  （即每个轮次最多一条，允许极少量重复判定）。
- **SC-004**: 托盘重启后，已查看历史保留率 100%（在保留上限内）。
- **SC-005**: 打开面板到首屏可用不超过 300 毫秒；「概览」首屏出数不超过 1 秒（CPU 首样本除外）。
- **SC-006**: 面板关闭时，通知与采样功能的后台 CPU 占用低于 1%。
- **SC-007**: 用户可以在不查阅文档的情况下，从设置页把通知从「标准」改为「安静」并验证生效。
- **SC-008**: 因通知投递失败而丢失的条目数为 0（失败仍保留在列表中）。

## Assumptions

- **目标用户**：单人使用本机 DSH 的开发者，同时并行 1–5 个会话，会切走窗口做别的事。
- **DSH 版本**：以本机安装的 `0.2.1-rc.5` 为契约基准；事件名与字段以该版本的宿主类型定义为准。
- **端口固定 3080**：沿用既有约束——登录 cookie 绑定 host:port，换端口会让浏览器静默掉登录。
- **托盘是主要入口**：默认开机自启；用户从终端直接启动 DSH 属可接受的次要路径（由 FR-034 兜底）。
- **不做远程推送**：本规格不含 ntfy / Telegram / 邮件等跨设备通道；如需要另立规格。
- **不做通知按钮动作**：Linux 通知服务对「操作按钮」的支持不一致，本规格只保证「点击通知」这一种交互。
- **不引入新的第三方运行时依赖**：跨平台能力以标准库与系统能力实现。
- **Windows 未在真机验证**：本规格要求的 Windows 等效能力，交付时必须显式标注验证状态，
  不得以「已支持」表述。
